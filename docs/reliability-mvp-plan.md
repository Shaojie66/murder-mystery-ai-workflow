## 1. 当前决策与事实边界

本轮按本地、单用户 Alpha 推进，首批目标用户为完成过至少一个剧本、正在创作新作品的独立作者，首批质量验证聚焦机制本。其他类型和已有阶段保留，暂不承诺通过同等质量验证。

核心价值假设：帮助作者保持事件真相、角色认知、线索和剧本材料一致，减少修改后的复核与返工。尚无证据支持“不穿帮”“直接商业发行”“快 5–10 倍”或稳定审计准确率等公开承诺。

本地存储不等于离线运行：使用云端模型时，相关上下文仍发送给模型服务商。本轮默认作者自带模型 API key；本次实施和验收只使用模拟模型，不读取实际 key，也不产生模型费用。

2026-10-24 的只读审查已运行现有测试，结果为 120 passed、1 条开发密钥提示。隔离复现仍发现矩阵降级失真、扩写材料丢失、审计误通过、SSE 协议与结束事件问题。测试数量不能替代核心流程、真实创作质量和多用户安全验收。

历史文档中的市场规模、竞品判断、付费意愿、种子用户、价格和收入预测，只有附可核验日期、样本与原始结果时才能升级为证据。

## 3. 首版范围与用户任务

核心任务：

1. 作者填写创意简报，确认机制、角色和事件。
2. 系统生成可校验的角色认知与证据关系，再生成 a/b 本、主持手册和结局。
3. 作者查看并修改内容；系统明确说明本次审计覆盖的文件及输入版本。
4. 审计定位问题，作者审阅修复建议；生成完成、审计完成和作者接受是不同结果。
5. 作者导出并检查试玩包，组织真实试玩，记录问题与后续修改。

| 本轮优先打通 | 暂缓新增投入 |
| --- | --- |
| CLI 与本地 Web 共用引擎；机制本；2 人原型与 6 人扩写 | 云端账号、云同步、实时协作、支付与订阅权益 |
| 结构化矩阵、角色 a/b 本、主持材料、审计定位 | 模板市场、发行对接、移动端编辑 |
| 失败不伪装成功、保留原作品、可恢复的重跑 | 新增图像/视频服务集成、宣发和运营能力扩展 |
| 试玩包与调用记录 | PostgreSQL、对象存储、K8s 等新增基础设施 |

阶段 3–8 的既有功能保留，本轮仅修复会破坏核心结果判定的问题，例如 PDF 未生成却显示成功。暂停不等于删除或撤回功能。

修改上游事实后自动标记全部下游材料过期，是后续目标；在没有可靠依赖版本记录前，不宣称已有此能力。本轮用明确的影响提示和用户显式选择的重新生成来避免无提示覆盖。

## 4. 已确认的工程问题与修复目标

| ID | 已复现或代码确认的问题 | 拟议行为与验收重点 |
| --- | --- | --- |
| R01 | 分步骤模板包含无关任务和未替换变量；JSON 示例与现有 schema 不符 | 每步仅含本步任务和必填上下文；渲染有残留变量即拒绝调用；输出匹配现有 schema |

| R03 | expand 未保留原两位角色正文，新角色部分失败仍切完整版 | 完整生成六人材料，校验保留约束；任一必要结果失败，现有作品与原型状态保持可用 |
| R04 | expand 后 JSON、b 本、DM 与结局可能维持旧事实；单次降级可能缺矩阵 | 扩写候选须包含一致的必要材料；材料不齐则失败，不宣称完整版完成 |
| R05 | audit 未读实际 b 本/DM/结局；普通表格 P0 可能计为零；豁免按数量抵扣 | 输入覆盖完整材料；输出结构化问题与定位；解析失败为“未完成”；豁免逐项匹配 |
| R06 | audit 可自动改写角色本，即使最终尚有严重问题 | 默认检查与修复建议；作者显式选择接受修复后才写入当前作品，不能把未解决结果标为通过 |
| R07 | SSE data 为 Python 文本，完成事件丢失；同步调用阻塞事件循环 | JSON 事件合同、可靠结束标记、完整消费、非阻塞执行与线程安全投递 |
| R08 | 运行与查询用不同 SSEManager；前端忽略 success=false；analyze 参数未贯通 | 单一任务状态来源；失败/取消/成功独立显示；反馈分析参数实际进入对应执行路径 |
| R09 | 包依赖机器专属绝对软链接 | 统一正常包导入、验证不依赖旧目录；移除软链接本身需另行批准 |
| R10 | init 目录和模型选择不一致；resume 恢复未持久化；PDF 失败仍成功 | CLI 与 Web 初始化遵循同一契约；恢复后能重新载入；必要文件实际生成后才完成 |
| R11 | 留资 JSON 返回 422，A/B 分流及 PV 计数有偏差，数据仅在内存 | 先修请求合同、分流与事件口径；持久化未经批准前不启动外部实验，不使用现有统计作付费依据 |
| R12 | 任意申请 token、共享项目目录、设置接口缺权限 | 继续限定本地单用户；公网与多用户发布作为独立安全项目，不以已有 token 等同真实登录 |

R01/R02/R05 涉及新的模型输出约束时，默认只做调用边界和内存对象校验，保留现有持久化模型。若方案需要改变已有 JSON 字段语义、增加迁移或覆盖旧资料，先单独说明并确认。

## 5. 最小技术路径与实施批次

保留现有 Python/FastAPI/React 结构，优先修现有合同。不在本轮引入新数据库、服务、全局依赖、任务平台或持久化 manifest。

| 批次 | 目标与主要模块 | 验收后才能进入的下一步 |
| --- | --- | --- |
| A：生成契约 | `prompts/loader.py`、对应模板、`wizard/schemas.py` 的现有约束、`truth_files.py`、阶段 2 保存路径及隔离测试；落实 R01/R02 | 非法模型输出不能成为已完成产物；合法矩阵保留认知与证据 |
| B：扩写与审计 | `cli/phase_runner.py`、`cli/commands.py`、审计模板与测试；落实 R03–R06 | 部分失败不损害原型；完整六人材料一致；审计有完整输入和可靠结论 |
| C：入口与 Web | CLI 向导、恢复、PDF 判定；Web 包导入、SSE、阶段 API、前端流消费与状态；落实 R07–R10 | 一次真实 HTTP 模拟执行，前端收到完整事件和正确最终结果 |
| D：试点准备 | 留资与统计合同 R11；修订研究招募和指标；明确 R12 的本地边界 | 核心闭环验收通过、研究人员/资料权限落实后，才能另行组织真人试点 |

这里的批次为依赖顺序，不是工期承诺。用户确认后先执行 A，验收合格后在已批准范围内推进 B/C。出现红线、持久化兼容性变化或超出范围的设计时，仅停住对应项并说明影响。

### 批次 A 的具体合同

- 每个生成步骤只接受其声明的输入；提示词渲染后若仍含未解析变量，返回明确错误。
- 保留现有角色与事件标识，JSON 示例必须通过当前 Pydantic 校验及业务完整性校验。
- 数量、角色标识、事件覆盖、认知状态、证据引用相互一致；空矩阵不能仅凭计数字段通过。
- 生成失败不得用默认“否”补齐未知认知，不得覆盖此前有效矩阵，不得把阶段标为完成。
- 旧 Markdown 转换入口与新内容生成分开；本批次不迁移已有作品、不新增持久化 schema。
- 只加入能够重现失真、缺字段、部分覆盖和变量残留的测试，不以断言实现细节代替行为验证。

### 批次 B 的候选提交与作者控制

- 批次 B 内先修审计合同，再修扩写，使扩写候选能够接受完整审查。
- 在内存或隔离候选文件中完成生成与校验；覆盖当前作品前必须具备全部必要结果及原内容可恢复副本。
- 六人扩写必须保留原两位角色的约束，并补齐他们在新增事件中的视角。
- 不以“新角色调用成功了几个”判断扩写完成；六人的 a/b 本、主持材料、结局与矩阵需共同验收。
- 对现有用户编辑过的材料，重新生成必须通过显式操作选择，并说明覆盖范围；自动批处理不得悄悄覆盖。
- 审计默认提供报告与修复建议，解析失败、材料缺失、严重问题未解决都不能显示通过。
- 多文件提交若需要新的目录布局或迁移来保证恢复，应暂停该部分，另提最小设计；不能在缺少一致性保证时声称已实现事务提交。

保留当前逐文件存储布局时，本轮只承诺模型失败和普通写入异常有明确失败与恢复路径，不承诺进程被强杀或断电时的多文件原子提交。断电级恢复需要单独设计并批准版本目录或 journal/manifest，不能以“已有备份”替代该保证。

### 批次 C 的任务与事件合同

- 一个作品同一时刻至多一个写入任务；状态查询、运行与取消使用同一个任务对象。
- 任务状态至少明确区分运行、成功、失败与取消；HTTP 200 或连接结束不代表业务成功。
- 后端发送的 `data` 必须可按 JSON 解析；完成事件必须送达，正常结束先消费队列再退出。
- 生成工作不能阻塞事件循环；若用线程承载同步引擎，队列投递必须走线程安全入口。
- 取消和断线采用明确语义：本地首版可不支持断点重连，但不能在页面停止等待时宣称底层调用已停止；任务结束前持续占用作品写锁。
- 非法阶段、缺失作品、重复运行、模型异常、失败结果、取消和反馈分析均有 HTTP/事件合同测试。
- 不依赖绝对软链接或同一模块的两个导入名称；在隔离导入环境中验证单实例。

## 6. 工程验收与回归

所有工程验收使用临时项目与模拟模型，不读取或修改实际作品，不访问云端服务。

| 场景 | 必须观察到的结果 |
| --- | --- |
| 模板缺输入或残留变量 | 调用模型前失败，明确指出缺失输入 |
| 模型返回非法/部分 JSON | 阶段失败，旧有效矩阵保持不变，不出现默认全“否”成功 |
| 合法原型矩阵 | 2×3 覆盖与证据引用正确，保存后重新读取一致 |
| 扩写任一必要调用失败 | 现有六类角色材料和矩阵保持有效，原型状态不被切换 |
| 完整扩写成功 | 六位角色包含原两位，JSON 与 a/b 本/DM/结局一致，必要产物齐全 |
| 审计发现表格 P0、结构化严重问题或解析错误 | 有问题或未完成，不返回通过 |
| 人工拒绝修复 | 当前作品不变；建议与报告可查看 |
| SSE 阶段成功/失败/取消 | 最终事件及字段完整，前端显示相同业务结果 |
| 长调用期间 | 状态/取消请求可被处理，不能阻塞整个服务 |
| session 恢复与 PDF 失败 | 恢复后可重新载入；缺必要 PDF 时明确失败 |
| 留资与统计 | JSON 合同可通过；一次访问只计一次；实验版本按访客稳定分配 |

回归命令：

```bash
PYTHONDONTWRITEBYTECODE=1 .venv/bin/python -m pytest tests/ -v -p no:cacheprovider
```

Web 改动后还需运行：

```bash
npm --prefix murder_wizard_web/frontend run build
```

仅有这些检查通过仍不能证明模型文笔、剧情质量或玩家体验合格。对发现的既有问题增加失败用例，修复后再通过；现有 120 项测试结果只作为基线。

## 7. 真人试点与产品验收

先完成工程验收，再安排 6 位目标创作者使用真实作品。作者试点与一次 6 位玩家试玩是两组不同任务，不合并计算为用户验证人数。

| 要验证的假设 | 方法 | 建议试点门槛 |
| --- | --- | --- |
| 作者可独立完成闭环 | 记录开发者介入；不由开发者代操作 | 至少 4/6 人完成 |
| 减少复核与返工 | 与原有“通用 AI + 文档”做配对任务，交叉安排顺序；包含审阅、重试与返工 | 总时间中位数减少至少 30%，严重错误不增加 |
| 创作者愿意继续使用 | 观察 14 天内是否主动带自己的内容再次使用 | 至少 3/6 人再次使用 |
| 作品可支持试玩 | 至少一个真实六人机制本，独立评审并实际试玩 | 材料完整；无阻断流程的关键矛盾；记录并复核试玩问题 |
| 有可执行的付费意愿 | 用户体验结果后，展示明确价格、服务范围和模型费用 | 至少 2 人接受真实付费试点；组织和收款另行授权 |

上述数值是建议的探索门槛，不是统计证明、已有成绩或宣传承诺。没有原流程基线时，先报告实测耗时；2 人原型不能证明六人平衡，一次六人试玩也不能证明普遍适用。

审计质量另设冻结样本：包含已知问题与无错误对照，由两名独立真人评审标注并裁决争议，分别报告精确率、召回率及原始误报/漏报数量。可先以精确率 ≥90%、召回率 ≥80% 为技术试点目标；须同时报告样本量和严重错误，不能只展示百分比。人工判定有严重问题时，模型的“通过”不改变该结论。

## 8. 付费与成本假设

本轮不实现支付、不包模型费用、不承诺无限生成。先记录完整可接受试玩包的所有生成、重试、审计与修复调用，以及人工支持时间；典型与高消耗样本分开报告，费用估算需与账单核对。

按作品付费、月订阅、自带 key 的工具服务均为候选。留邮箱、点击升级与口头意愿只记兴趣，不能计作注册、付费或产品留存。

是否进入 SaaS 探索，取决于核心价值、真实质量、再次使用与成本结果。届时再单独设计真实身份、作品归属、隔离、持久化、预算限制和发布方案。

## 9. 批准边界与实施前确认

本次已获授权的动作：把审查结论收敛为文档，调整当前方案入口和任务状态。当前没有源代码修复、数据变更或公开发布。

请求确认的最小实施范围：按本文件 A → B → C 修复现有本地核心闭环，先执行批次 A 的输入输出合同与隔离回归；D 的合同修复可在核心验收后执行，真人联系、收集资料、付费及部署不包含在实施授权中。

以下动作即使确认本方案，也须依据用户红线单独批准：

- 删除文件、目录或 Git 历史，包括移除既有绝对软链接；
- 修改密钥、token、`.env`、CI/CD 或系统配置，安装新的全局依赖；
- 数据库 schema 变更或数据迁移；本轮不包含已有作品迁移或持久化 JSON 结构重设计，若确有必要，先更新对应方案与兼容性评估；
- push、rebase、reset --hard、强制推送或任何公开发布。

方案确认不代表这些动作已获授权。实施中只在遇到对应红线或新增范围时提出具体问题，不反复确认已批准的普通修复。
